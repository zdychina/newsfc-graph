# 配置生成 SOP

> **管道设计原则**：本 SOP 是数据流管道——每一步的输入依赖上一步的产出物。图谱知识是**唯一权威来源**，现网仅用于复用判断和命名参考。没有上一步产出物，下一步无法执行。
>
> | 模块 | 何时读 | 承载内容 |
> |---|---|---|
> | `图谱接口.md` | 调图谱时 | 当前图谱传输实现、调用参数、工具能力、下钻四步、ID 格式 |
> | `图谱导航.md` | 理解图谱层级时 | 四层架构、每层语义、检索纪律 |
> | `现网搜索.md` | 查现网时 | mml_extract.py 用法、搜索计划、搜索日志、参数筛选陷阱 |
> | `命令级约束.md` | LLD 规划 + 配置生成时 | AtomTask/MMLCommand 下钻、参数引用约束校验、优先级语义 |
> | `common/AI-MML核查流程.md` | Stage 6 核查（无 `aimml-check` 时） | 直接调用 coremaster configcheck 接口的核查流程（后备路径） |

---

## 1. 定位

Agent 根据用户需求描述和现网配置脚本，经过**图谱定位 → 现网映射 → 方案确认 → 参数规划 → 配置生成与核查**，输出可直接执行的 MML 配置脚本。

本 SOP **业务域无关**——业务域/场景/方案由后端图谱动态定义，新增业务域/场景/方案 = 后端图谱加对象，**本 SOP 不改**。

---

## 2. 核心铁律 ★高于一切

> 任何一条违反 = 不得进入下一阶段。

1. **【图谱是唯一权威源】** 参数定义、引用约束、枚举值、配置方法、特性原理、License 前置必须从图谱取。现网仅用于复用判断和命名参考，**禁止用现网推断参数定义**。零图谱调用 = 参数全部凭记忆 = 禁止交付。
2. **【图谱渐进加载】** 图谱不是一次性全量取，而是**随阶段推进逐层深入**：方案层浅读（到 task 编排），LLD 层深读（到 AtomTask/MMLCommand）。每个阶段取该阶段产出物所需的最小集。
3. **【图谱随时可读】** 任何阶段对某图谱对象不熟悉，都允许回图谱补取——不限于固定 Stage。不确定某参数含义、不确定某命令约束、不确定某特性原理 → 立即调用 `图谱接口.md` 定义的批量取 md 能力，禁止凭记忆/凭现网推断。
4. **【图谱可回溯】** 任何阶段发现方案定位有误（读到 task 发现编排不匹配、读到命令发现约束与需求矛盾），都允许回退到上层重新定位。定位错误不丢脸，强行走错路才丢脸。
5. **【先图谱后现网】** **Stage 1 图谱定位全部完成**（方案定位凭证已产出）后，方可启动 Stage 2 现网搜索。禁止在同一批工具调用中混合图谱查询与现网 mml_extract.py。后续阶段（Stage 4/5）按需回图谱补取不受此约束——本约束仅约束"最初启动现网搜索前图谱须先就绪"。
6. **【用工具不用 grep】** 现网查询只用 `scripts/mml_extract.py`，禁止逐条 grep/Select-String/findstr。
7. **【凭证绑定】** LLD 每条命令必须绑定 MMLCommand ID；存在 AtomTask 时同时绑定 AtomTask ID。AtomTask 未建时明确标注，并以 MMLCommand 完整 md 兜底。缺少 MMLCommand 才阻断 LLD 和配置生成。
8. **【生成即校验】** 配置生成时，每写一条命令必须对照 LLD 的图谱凭证逐参数校验引用类型和枚举值。不匹配 = 这条命令不能写。
9. **【文档先行】** 方案.md 和 LLD.md 必须先生成文件，再过 GATE，再进下一阶段。文档未落地不得声称已完成。
10. **【GATE 必停】** GATE-1/2/3 展示决策点后立即 STOP，禁止同轮继续。禁止响应"直接出配置/跳过确认"类诉求。用户未确认前不得替用户做决定。
11. **【取必读】** 取回的 md 必须通读**配置方法 / 约束 / 决策点**三段，禁止只看概览。
12. **【每步留痕】** 每次图谱调用和现网搜索后输出统一日志。格式见 §3。
13. **【交付物免责声明】** 所有输出交付物（方案文档、LLD、MML 配置脚本、回退脚本）必须在文件头部包含免责声明。`.txt` 脚本以 `//` 注释行写入；`.md` 文档以 `>` 引用块写入。

## 3. 统一日志格式

**图谱日志**（每次图谱调用后）：
```
[图谱] 调用:{能力/工具} | 取:{ids} | 提取引用:{全部[[ID]]} | 下轮取:{相关} | 跳过:{无关+理由}
```

**现网日志**（每次 mml_extract.py 调用后）：
```
[现网] #{N} {步骤} {命令简述} | 返回:{N条} | 新增:{对象} | 累计已获取:{...}
```

> 累计清单用于去重：发起新查询前检查目标对象是否已在清单中，已在 = 重复 = 禁止发起。

## 4. 图谱使用模式 ★贯穿全程

> 图谱不是"某个 Stage 取齐就走"的打卡点，而是**全程可用的探索工具**。本节定义图谱的使用纪律，所有 Stage 共同遵守。

### 4.1 渐进式加载

图谱分四层（业务层/任务层/特性层/命令层），**随阶段推进逐层深入**：

| 阶段 | 必须取到 | 按需补取 |
|---|---|---|
| Stage 1 图谱定位 | 业务层（域→场景→方案）+ 任务层（task 编排概览） | 命令层（决策点涉及命令参数时）、Feature（需理解原理时）、License（前置检查时） |
| Stage 4 LLD 规划 | 命令层 MMLCommand 必读；检索 AtomTask，已建则必读、未建则标注 | Feature（配置方法需理解原理时）、ConfigObject（差异分析归类时） |
| Stage 5 配置生成 | 对照已沉淀的图谱知识表校验 | 任何发现缺口的命令 → 回图谱补取 |
| 任意阶段 | — | 对某对象不熟悉 → 立即补取（铁律3） |

> **底线**：LLD 产出前，本次配置涉及的每条命令必须已取到 MMLCommand；存在 AtomTask 的命令还要同时读取 AtomTask。这是铁律7（凭证绑定）的前提——没有 MMLCommand ID 填不出图谱来源列。

### 4.2 回溯机制

定位不是一次定终身。以下情况允许回退重定位：

| 触发信号 | 回退到 | 动作 |
|---|---|---|
| 读到 task 发现编排与用户需求不匹配 | Stage 1 场景层 | 重新匹配场景/方案，或向用户确认是否换方案 |
| 读到命令发现约束与需求矛盾（如引用约束排除了用户要复用的对象） | Stage 1 方案层 | 重新匹配方案，或向用户说明矛盾并协商 |
| 现网搜索发现现网结构与图谱编排严重不符 | Stage 1 | 向用户确认现网是否有特殊配置，或重新定位 |
| 配置生成校验发现某命令图谱未建 | Stage 4 | 优先补取 AtomTask；AtomTask 未建则标注后以 MMLCommand 完整 md 兜底；MMLCommand 也缺失才阻断 |

> 回溯时必须向用户说明原因和影响，不得静默回退。

### 4.3 图谱兜底纪律

为确保图谱知识最大化利用，以下场景**必须**读图谱：

1. **不确定就取**：对任何图谱对象（命令/参数/特性/约束）的含义不确定时，取该对象 md，禁止凭记忆推断。
2. **约束必查**：生成配置前，每条命令的 MMLCommand 必须实查；AtomTask 已建时同时读取其场景化方法和引用约束，未建时标注后仅校验 MMLCommand 已声明约束，不靠记忆补造。
3. **特性原理按需查**：配置方法依赖某特性原理时（如计费流程、限速机制），取 Feature md 理解原理再配，不靠经验拼。
4. **License 前置查**：方案/特性提及 License 门控时，取 License 对象确认前置条件，不跳过。
5. **差异分析查 ConfigObject**：判断现网对象复用/新建/修改/删除时，取 ConfigObject md 确认对象类型归属，不靠名字猜。

## 5. 管道流程总览

```
Stage 1: 图谱定位        → 产出: 方案定位凭证（域/场景/方案 + task编排概览）
  ↓ 依赖: 方案定位凭证
Stage 2: 现网映射        → 产出: 现网对象清单（复用/新建/修改/删除）
  ↓ 依赖: 方案定位凭证 + 现网对象清单
Stage 3: 方案确认【GATE-1】→ 产出: 方案.md（用户确认"做什么"）
  ↓ 依赖: 方案.md 已确认
Stage 4: 参数规划【GATE-2】→ 产出: LLD.md（下钻到命令层，图谱知识表内嵌LLD，参数绑定图谱凭证）
  ↓ 依赖: LLD.md 已确认
Stage 5: 配置生成        → 产出: 配置脚本（对照图谱逐参数校验 + 按需补取）
  ↓ 依赖: 配置脚本已生成
Stage 6: 核查交付【GATE-3】→ 产出: 核查通过的可执行脚本
```

### 阶段进入条件总表

| 阶段 | 进入前必须满足 | 完成标志 | 未满足时 |
|---|---|---|---|
| Stage 1 | 图谱服务可访问 | 锁定 {域}/{场景}/{方案} + task 编排概览 | STOP，要求补需求关键词 |
| Stage 2 | Stage 1 已锁方案 | 现网对象清单产出 | STOP，要求补现网脚本 |
| Stage 3 | Stage 1 + Stage 2 均已完成 | **方案.md 已生成** 并展示 | STOP，禁止进入 Stage 4 |
| Stage 4 | **用户已确认 GATE-1** | **LLD.md 已生成**（参数表含图谱来源列） | STOP，禁止进入 Stage 5 |
| Stage 5 | **LLD.md 已确认** | 配置脚本生成（每条命令已校验） | STOP，禁止直接交付 |
| Stage 6 | Stage 5 配置脚本已生成 | 核查通过 + 用户确认 | STOP，禁止进入交付 |

> **用户交互规则**：专业平实、表格展示、追问说明原因与影响。3 个 GATE 必须 STOP 等用户确认。GATE 展示时逐条列决策点（每条：是什么、为什么需用户定、有哪些选项、不定的后果），严禁只笼统问"是否继续"。用户中途可"暂停/重新开始/换业务域/换场景/到此为止"。

## 6. Stage 1: 图谱定位

### 产出物
**方案定位凭证**（写入对话 + 后续 Stage 引用）：
```
业务域: {BusinessDomain ID}
场景: {NetworkScenario ID}
方案: {ConfigurationSolution ID}
方案核心编排: {方案 md 概览}
task 编排概览: {相关 FeatureTask/CompoundTask/AtomTask ID + 各自角色}
编排序列: {按方案「配置编排」展开的有序步骤；方案无该段时注明“按依赖推导”}
```

### 步骤
1. **取全部业务域 md**：调用 `图谱接口.md` 定义的业务域入口。按用户需求关键词匹配业务域，锁定 `{业务域}`。输出 [图谱] 日志。
2. **读域 md → 取场景清单**：提 `[[NetworkScenario@*]]`（域 md 已在手，不必重复调用）。按子场景关键词匹配锁定 `{场景}`。
3. **读场景 md → 决策点路由表 + 方案候选**：调用批量取 md 能力读取场景。场景 md 含决策点路由表（业务诉求→推荐方案）+ `[[ConfigurationSolution@*]]`。按决策点表 + 用户诉求匹配方案。输出 [图谱] 日志。
4. **读方案 md → 锁定方案**：调用批量取 md 能力读取候选方案，读概览确认。锁定 `{方案}`。输出 [图谱] 日志。
5. **取相关 task 编排概览**：从方案 md 提取 `[[{nf}@CompoundTask@*]]` / `[[{nf}@FeatureTask@*]]` / `[[{nf}@AtomTask@*]]` 引用（`{nf}` 为任意网元，如 UDG、UNC；跨网元方案两侧都要取），按用户意图筛选相关 task，批量取 task md 并读编排概览。输出 [图谱] 日志。
6. **展开配置编排**：方案 md 有 `### 配置编排` 时，按 `图谱导航.md` §3.1 逐行展开（条件判定、FT 激活方法、省略 / 后移 / 仅步骤 / 重复 / 增量），得到**编排序列**。引用 FT 的行要取 FT md，读「激活方法与参数差异」中对应名称的行。条件无法从需求判定的，列为 GATE-1 的决策点。方案没有该段时，注明“按依赖推导”。

> **本阶段读到 task 层即可**（方案确认"做什么"不需要命令参数细节）。但以下情况**按需下钻命令层**（铁律3/§4.1）：
> - 决策点涉及命令参数级选择（如"是否启用某参数"需看 MMLCommand 参数定义）
> - 需理解某特性原理才能判断方案是否匹配（取 Feature md）
> - 需确认 License 前置（取 License 对象）

> 下钻四步循环见 `图谱接口.md`、`图谱导航.md` §6。每次图谱调用后必须输出 [图谱] 日志（铁律12）。

### 完成标志
- 已锁定 {业务域}/{场景}/{方案}
- task 编排概览已输出
- 编排序列已输出（或已注明“按依赖推导”）
- 方案定位凭证已输出

### 未满足
- STOP，要求补需求关键词

### 修改对象
| 对象类型 | 对象名 | 修改内容 | 修改依据 |

### 删除对象
| 对象类型 | 对象名 | 删除依据 |
```

### 进入门控
- Stage 1 方案定位凭证已产出（铁律5：先图谱后现网）

### 步骤
1. **现网脚本前置检查**：未提供路径 → STOP；用 Glob/`ls` 验证存在且可读，严禁 Read 工具（数万行必溢出）。
2. **现网搜索**：流程详见 `现网搜索.md`（搜索计划、mml_extract.py 用法、参数筛选陷阱、搜索日志）。纪律要点：
   - 先输出搜索计划，再执行
   - 批量拉取优先，一次调用能拿到的数据不分两次
   - trace 结果必须完整消费
   - 每次 mml_extract.py 后输出 [现网] 日志
3. **差异分析**：对每个 ConfigObject 判断 复用 / 修改 / 新建 / 删除。判断对象类型归属时取 ConfigObject md（§4.3-5），不靠名字猜。

> **★现网数据的边界**（铁律1）：现网数据仅用于——① 判断对象是否已存在（复用决策）② 参考命名规律（新对象命名）③ 参考优先级数值（排序参考）。**禁止用现网数据确定参数定义、引用约束、枚举值**——那是图谱的职责。

### 完成标志
- 现网对象清单已产出（复用/新建/修改/删除分类清晰）
- 每个现网日志已输出

### 未满足
- STOP，要求补现网脚本

**`xxx方案.md`**——必须先生成文件（铁律9）

```

- `xxx方案.md` 已生成文件
- GATE-1 已展示并 STOP

### 路由
- 用户确认 → Stage 4
- 要求修正 → 回 Stage 1/2 修正后重新展示
- 换方案 → 回 Stage 1 重新定位

> **禁止**：确认前执行 Stage 4 或生成 LLD 或生成任何配置命令。本轮展示方案.md + 发出 GATE-1 后必须结束。

## 9. Stage 4: 参数规划【GATE-2】★图谱深读

> 本阶段是图谱深读的时机——方案已确认，下钻到命令层不会白做。产出的图谱知识表内嵌于 LLD，是 Stage 5 配置生成的唯一校验基准。

### 产出物
**`xxxLLD.md`**——参数表必须包含**图谱来源列**（铁律7）；MMLCommand ID 必填，AtomTask ID 有则同时标注、无则写“未建”

### 进入门控 ★不满足禁止产出 LLD

| # | 门控项 | 检查方式 |
|---|---|---|
| G4-1 | 已对全部命令检索 AtomTask；存在的全部读取，未建的已标注 | 对照命令清单，每条命令都有 AtomTask ID 或“未建”记录 |
| G4-2 | 已下钻本次配置所需全部 MMLCommand（取枚举/类型/约束） | 对照命令清单，每个命令都有 MMLCommand ID |
| G4-3 | 已校验图谱中明确声明的全部引用约束；未声明的已记录风险 | 校验表逐项为“通过”或“约束未提供（AtomTask未建）”，不得虚构 |
| G4-4 | 已输出 [图谱] 日志确认命令层取齐 | 铁律12 |

> **门控证据**：满足门控时必须贴出图谱知识表（命令定义表 + 参数约束表）。没有图谱知识表 = 门控未通过 = 禁止产出 LLD。
> 下钻流程和校验方法详见 `命令级约束.md`。

### 步骤

**Step A — 深读图谱：下钻 AtomTask + MMLCommand**

这是本阶段的核心动作——从 Stage 1 的 task 层继续下钻到命令层（详见 `命令级约束.md` §2）：

1. 列出本次配置需要的全部命令（按方案.md §3 编排序列展开：CompoundTask 步骤表 + FeatureTask 配置流程，省略的步骤不计）
2. 通过 `图谱接口.md` 定义的批量取 md 能力读取已建的对应 AtomTask（取配置方法+引用约束），未建的明确标注
3. 从 AtomTask ref 提取 MMLCommand 引用，再批量取 MMLCommand md（取枚举/类型/约束）
4. 构建图谱知识表（命令定义表 + 参数约束表），每行标注来源 ID
5. 完成参数引用约束校验表（详见 `命令级约束.md` §3）
6. 每步输出 [图谱] 日志

> **若某命令没有对应 AtomTask**（图谱未建）：直接读取 MMLCommand 完整 md 作为兜底，
> 在知识表和 LLD 中标注“AtomTask 未建”。可以继续生成，但不得虚构 AtomTask 才可能提供的
> 场景化配置方法或引用约束；参数定义、类型、枚举和已有约束以 MMLCommand 原文为准。

**Step B — 复用 Stage 2 现网数据**

Stage 2 已收集的参数格式、命名规律、对象清单直接复用，禁止重复查现网。仅 Stage 2 未覆盖的参数才需补充。

**Step C — 参数分两类**

- **固定参数**：不随本次规划变化，从现网脚本、图谱规则、命令默认值、命名规律回填。无法可靠确定则降级为变化参数。
- **变化参数**：随用户意图/规划数据变化，需用户指定/确认。

**Step D — 优先级分析**（涉及有序规则时必须执行）

从 task/命令 md 的 Rule 段确认优先级机制；用 Stage 2 已收集的现网 PRIORITY 值排序；优先级数值语义由图谱规则定义，禁凭记忆。用户确认后才能生成带优先级的命令。

**Step E — 产出 LLD.md**

```markdown
# {项目/需求名}LLD
> ⚠️ 本文件由 AI 辅助生成，仅供参考。正式执行前需经人工审查和验证，确认无误后方可使用。
## 1. 方案与范围
## 2. 现网依赖与命名继承
## 3. 图谱知识表（命令定义 + 参数约束）  ← 从 Step A 沉淀
## 4. 固定参数
## 5. 变化参数（待用户补充/确认）
## 6. 优先级分析
## 7. 多网元一致性约束
## 8. 待用户确认项
```

LLD 参数表格式（★图谱来源列是铁律7的强制要求）：

```markdown
## LLD规划数据表 — {方案名}
### 网元: {网元类型1}
| 命令 | 参数 | 参数类型 | 值 | 图谱来源 | 状态 | 说明 |
| ADD FLOWFILTERGRP | FLOWFILTERNAME | String | fg_ytb_tik | UDG@AtomTask@xxx, UDG@MMLCommand@xxx | 待确认 | 引用约束:只能引用ADD FLOWFILTER产出的对象 |
| ADD URR | URRID | Integer | 1330 | UDG@AtomTask@yyy, UDG@MMLCommand@ADD URR | 待确认 | RG×10命名规律 |
| ADD URR | RG | Integer | 133 | UDG@AtomTask@yyy, UDG@MMLCommand@ADD URR | 固定 | 用户指定 |
| ADD DEMO | MODE | Enum | ENABLE | AtomTask未建, UDG@MMLCommand@ADD DEMO | 固定 | 以MMLCommand完整md兜底 |

### 全局参数（多网元共用，必须一致）
| 参数 | 参数类型 | 网元1侧 | 网元2侧 | 图谱来源 | 状态 | 说明 |
```

> **★图谱来源列的作用**（铁律7）：该列是"读图谱"的证据。无图谱来源 = 参数凭记忆 = 违反铁律1。Stage 5 配置生成时，必须对照此列逐参数校验。

**Step F — GATE-2 展示**

展示 LLD.md，逐条列变化参数与待确认项（每项给选项+影响），然后 STOP：
```
参数校验已通过。请检查 xxxLLD.md，确认无误后回复"确认"，将进入配置生成。
```

### 完成标志
- `xxxLLD.md` 已生成文件（参数表含图谱来源列）
- G4-1~G4-4 全部满足
- GATE-2 已展示并 STOP

### 路由
- 用户确认 → Stage 5
- 要求修改 → 修正后重新校验
- 发现约束矛盾 → 回 Stage 1 重新定位（§4.2 回溯机制）

> **禁止**：确认前执行 Stage 5 或生成 MML。

## 10. Stage 5: 配置生成

### 产出物
每网元 `.txt` 配置文件（每条命令已对照图谱校验）

### 进入门控
- **LLD.md 已用户确认**（GATE-2 通过）

### 步骤

**Step A — 逐命令生成 + 即时校验**（铁律8）

对 LLD 中的每条命令，执行以下校验循环：

```
对每条命令 C（按 task 编排顺序）:
  1. 从 LLD 取该命令的全部参数值
  2. 从 LLD 图谱来源列取该命令的 MMLCommand ID，以及存在时的 AtomTask ID
  3. 对照 MMLCommand md 逐参数校验:
     □ 引用类型: 有 AtomTask 时是否符合其引用约束；无 AtomTask 时是否符合 MMLCommand 已声明约束?
     □ 枚举值: 参数值是否在 MMLCommand CommandParameter 枚举内?
     □ 必填项: 所有 Mandatory 参数是否都已赋值?
     □ 联动关系: 选了A参数则B参数是否已填?
  4. 全部通过 → 写入配置文件
     任一不通过 → STOP, 标注错误, 回 Stage 4 修正 LLD
```

> **★生成即校验是铁律8的核心**。不是写完所有命令再回头核查，而是**写一条校验一条**。核查报错才发现引用错误 = 本阶段失败。

> **★按需补取**（铁律3）：若发现某命令的 MMLCommand 在 Stage 4 未取，立即回图谱补取，禁止凭记忆生成。补取后输出 [图谱] 日志。

**Step B — 命令编排排列**

**按方案.md §3 的编排序列排列**：序列中每一行按其 Task 的内部顺序展开（FT 配置流程 / CT 步骤表），省略的步骤不生成，后移的步骤只在目标行生成一次。方案未声明编排顺序（序列注明“按依赖推导”）时，才退回“底层先于上层、被引用者先于引用者”的依赖顺序。

**Step C — 命令完备性检查**

逐个 CompoundTask 核对其 md 步骤表，确认每步命令都已出现。对编排序列中的每个 FT：所选激活方法下的每一步，要么已生成，要么在序列中标为“省略”；标为“后移”的步骤恰好生成一次，且位置在目标行。

**Step D — 内置图谱 Rule 约束**

方案 BusinessRule + 命令 CommandRule + 任务 TaskRule，生成时即遵守。

### 校验时的硬约束
- 严格编排顺序：按方案的编排序列排列命令（方案未声明时按任务层依赖顺序）
- 动网保守：现网对象修改必须有用户确认
- 命名遵循现网：新对象命名沿用现网规律
- 跨网元一致：多网元共用参数必须一致

### 硬性禁止
- 禁止在缺少方案.md 或 LLD.md 时直接生成 MML
- 禁止用"聊天中已确认"替代文档存在性检查
- 禁止跳过 GATE-1/GATE-2

### 完成标志
- 配置脚本已生成（每条命令已校验）

### 产出
```
配置文件已生成（每条命令已对照图谱校验）。将进入 AI MML 核查。
```

## 11. Stage 6: 核查交付【GATE-3】

### Step A — AI MML 核查

**优先调用内网已提供的独立 SKILL `aimml-check`**，提供：网元类型、版本、MOP 脚本路径、现网脚本路径。

**运行环境中没有 `aimml-check` 时**，按 `common/AI-MML核查流程.md` 直接调用 coremaster configcheck 接口核查（凭据与 reference 算子表由部署环境提供；缺失时停止并报告，不跳过核查）。两条路径的结果处理规则相同，见下。

结果处理：
- **核查通过**（语法 0 + 语义 0）→ Step B
- **语法错误**：必须修正，修正后重新核查
- **语义错误（真实）**：必须修正，修正后重新核查
- **语义错误（可能误报）**：追踪间接引用链判断，确认引用链完整则判定误报，向用户说明
- **修正循环**：修正后重新核查直到通过或用户接受

### Step B — GATE-3 展示

核查通过后将核查报告 + 配置脚本一并向用户展示。展示后 STOP：
```
以上配置脚本已通过核查。请确认无误后回复"确认"，我将输出最终交付物。
```

### Step C — 输出交付

用户确认后，输出最终交付物，并清理中间文件：

| 文件 | 内容 | 格式 | 保留/清理 |
|---|---|---|---|
| 各网元配置脚本 | 可执行 MML，按 task 编排顺序 | `.txt` | 保留 |
| 校验脚本 | LST/DSP 校验命令 + 预期结果 | `.txt` | 保留 |
| 方案文档 | 方案决策 + 任务编排 + 风险 | `.md` | 保留 |
| LLD 文档 | 规划数据表（含图谱来源列） | `.md` | 保留 |
| 变更摘要 | 新建/修改/复用/删除对象清单 + 注意事项 | `.md` | 保留 |
| mml_extract 缓存 | 搜索结果缓存 | - | **清理** |
| 核查临时文件 | AI MML 核查中间输出 | - | **清理** |
| 搜索结果保存文件 | 任何为绕过读取而创建的中间文件 | - | **清理** |

> 配置脚本**必须是 `.txt` 后缀**。注释**必须 `//` 开头**。头部用 `//` 注明业务域、场景、方案、网元、决策点、生成时间；命令按 `// [Task ID]` 分段。头部 `//` 注释段同时包含免责声明（铁律13）。

### 路由
- 确认 → 输出交付物 + 清理
- 要求修改 → 回对应 Stage 修正后重新核查

## 12. 扩展与演进（本 SOP 永不改）

- **新增业务域/场景/方案**：后端图谱加对象，本 SOP 不改。
- **图谱加载方式演进**：传输协议或图谱工具变化时，只替换/修改 `图谱接口.md`，本 SOP 不改。
- **核查能力**：优先由内网已提供的独立 SKILL `aimml-check` 承载；没有时按 `common/AI-MML核查流程.md` 直接调用接口。接口或凭据变化时，只改该文件，本 SOP 不改。
- **现网搜索语法演进**：只改 `现网搜索.md`，本 SOP 不改。
- **命令级约束演进**：只改 `命令级约束.md`，本 SOP 不改。
