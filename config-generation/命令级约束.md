# 命令级约束模块

> Stage 4 参数规划（LLD）+ Stage 5 配置生成时读取。承载 AtomTask/MMLCommand 下钻流程、参数引用约束校验、优先级语义。
> 本模块从 SKILL.md 拆出。SKILL.md 的 Stage 4 门控（G4-1~G4-4）和 Stage 5 校验循环指向本文件。
> 图谱渐进式加载：Stage 1 读到 task 层即可，Stage 4 才深读到 AtomTask + MMLCommand（见 SKILL.md §4.1）。

---

## 1. 为什么优先读取 AtomTask，并始终读取 MMLCommand

**AtomTask**（命令级原子）和 **MMLCommand**（命令层）是两个不同粒度的知识源。MMLCommand
是命令生成的必备依据；AtomTask 已建时必须同时读取，未建时由 MMLCommand 完整 md 兜底：

| 知识源 | 提供什么 | 缺失后果 |
|---|---|---|
| **AtomTask** | ① 场景化配置方法 ② **参数引用约束** ③ 命令级 critical 约束 ④ 决策点 | 已建却跳过会丢失场景化方法和增强约束；未建时须明确标注 |
| **MMLCommand** | 命令原文 + **参数定义**（CommandParameter，含枚举值/类型/已有约束） | 必备兜底；缺失时不得生成该命令 |

> **SKILL 铁律1 要求**：参数定义、引用约束、枚举值、配置方法必须从图谱取。有 AtomTask
> 时先取其场景化方法和引用约束，再读 MMLCommand；无 AtomTask 时完整读取 MMLCommand 兜底。

## 2. Stage 4 下钻流程 ★图谱深读的必经环节

> Stage 4 是图谱深读的时机——方案已确认（GATE-1 通过），下钻到命令层不会白做。产出的图谱知识表内嵌于 LLD，是 Stage 5 校验的唯一基准。跳过本环节 = LLD 无法产出 = 后续无法执行。

### Step A: 下钻任务层（取配置方法 + 引用约束）

1. 列出本次配置生成需要用到的**所有命令**（从方案.md §3 编排序列展开后的步骤确定，含 CompoundTask 步骤表与 FeatureTask 配置流程；省略的步骤不计）
2. 找到这些命令对应的 `[[{nf}@AtomTask@*]]` 引用 ID（`{nf}` 为任意网元，如 UDG、UNC；从 CompoundTask/FeatureTask 的 md 正文提取）
3. 调用 `图谱接口.md` 定义的批量取 md 能力获取 AtomTask md
4. 通读每个 AtomTask 的：
   - **配置方法**（参数取值维度、联动关系、典型脚本）
   - **约束**（critical 项，尤其是**参数引用约束**——哪个参数只能引用哪种对象）
   - **决策点**（影响本次配置的必须确认）
5. 输出 [图谱] 日志确认已取齐 AtomTask 层知识

### Step B: 下钻命令层（取参数枚举/类型）

1. 从 AtomTask 的 ref 字段提取 `[[{nf}@MMLCommand@*]]` 引用 ID
2. 调用同一批量取 md 能力获取这些 MMLCommand md
3. **从 CommandParameter 字段取枚举值、类型、约束**——禁凭记忆、禁从现网推断枚举值
4. 输出 [图谱] 日志确认已取齐命令层知识

> **若某命令没有对应 AtomTask**（图谱未建）：直接追溯 MMLCommand 完整 md，并在知识表
> 和 LLD 标注“AtomTask 未建”。该命令可以继续生成，但不得虚构 AtomTask 才可能提供的
> 场景化配置方法或引用约束；MMLCommand 也缺失时才阻断。

### Step C: 构建图谱知识表

基于 Step A/B 取回的图谱知识，构建两张表。**这两张表是 Stage 4 LLD 的唯一参数来源**：

**命令定义表**：
```markdown
| 命令 | AtomTask ID（可为未建） | MMLCommand ID（必填） | 用途 | 配置方法要点 |
| ADD FLOWFILTERGRP | UDG@AtomTask@xxx | UDG@MMLCommand@xxx | 创建流过滤组 | FLOWFILTERNAME引用ADD FLOWFILTER产出的对象 |
| ADD DEMO | 未建 | UDG@MMLCommand@ADD DEMO | 示例用途 | 以MMLCommand完整md兜底 |
```

**参数约束表**：
```markdown
| 命令 | 参数 | 类型 | 必填 | 枚举值 | 引用约束 | 来源 |
| ADD FLOWFILTERGRP | FLOWFILTERNAME | String | 是 | - | 只能引用ADD FLOWFILTER创建的对象 | UDG@AtomTask@xxx |
| ADD URR | OFFMETERINGTYPE | Enum | 是 | VOLUME/SESSION/TIME | - | UDG@MMLCommand@yyy |
```

> 每行参数约束必须标注来源 ID。无来源 = 凭记忆 = 违反铁律1。

## 3. 参数引用约束校验 ★最常被跳过的环节

> Pipeline 审计显示：Agent 从方案直接跳到 LLD，完全未做引用约束校验，导致生成配置时把 FLOWFILTERGRP 名字填进了 FLOWFILTERNAME 参数——因为没读 AtomTask 知道"FLOWFILTERNAME 只能引用 ADD FLOWFILTER 创建的对象"。

### 什么时候校验

**在 Stage 4 构建图谱知识表时就完成校验**，而不是等到 Stage 5 配置生成时才回头查。

### 校验方法

对图谱知识表中每个带"引用约束"的参数，在 Stage 4 就明确记录约束内容。Stage 5 生成时，直接对照约束校验实际引用的对象类型。

约束来源的两种形态：
- AtomTask 约束描述为"该参数引用 ADD X 命令产出的对象" → 实际引用的对象**必须**是由 ADD X 创建的
- AtomTask 约束描述为"该参数只能引用 Y 类型的对象" → 实际引用的对象**必须**是 Y 类型

### 引用约束校验表（Stage 4 产出，Stage 5 复用）

```markdown
| 引用参数 | 所在命令 | 引用约束(来自AtomTask) | 实际引用对象 | 对象创建命令 | 校验结果 |
|---|---|---|---|---|---|
| FLOWFILTERNAME | ADD FLOWFILTERGRP | 只能引用ADD FLOWFILTER创建的对象 | fg_ytb_tik | ADD FLOWFILTER | ✅ |
| POLICYNAME | ADD RULE | 只能引用ADD PCCPOLICYGRP创建的对象 | cg_tkrs_nu_1800 | ADD PCCPOLICYGRP | ✅ |
| URRGROUPNAME | ADD PCCPOLICYGRP | 只能引用ADD URRGROUP创建的对象 | ppg_tkrs_nu_1800 | ADD URRGROUP | ✅ |
```

> 校验不通过 = 参数引用错误 = 必须在 Stage 4 就修正引用对象，不能带到 Stage 5。
> AtomTask 未建且 MMLCommand 未声明某项引用约束时，在表中记
> `约束未提供（AtomTask未建）` 并作为风险随 LLD 展示；不得虚构约束，也不因这一项
> 单独阻断。MMLCommand 本身缺失时才阻断该命令。

## 4. 优先级语义 ★禁凭记忆

涉及有序规则（如 RULE 的 PRIORITY 参数）时：

1. **优先级机制**从 task/命令 md 的 Rule 段确认（是否有优先级、优先级方向）
2. **优先级数值语义**（越小越高 / 越大越高）由图谱规则定义，禁凭记忆
3. 用 Stage 2 已收集的现网 PRIORITY 值排序分析
4. **用户确认后才能生成带优先级的命令**——展示现有优先级值 + 新规则应插入的位置，让用户确认

示例：
```
优先级分析
现有规则优先级：
  l_tk_nu_1265: PRIORITY=2121
  l_rs_s12mbilled_1709: PRIORITY=2130
  l_im_nu_100: PRIORITY=2299
用户要求顺序：l_tk_nu_1265 > l_rs_s12mbilled_1709 > L_TKRS_Nu_1800 > l_im_nu_100
→ L_TKRS_Nu_1800 的 PRIORITY 应在 2130~2299 之间
→ 推荐 2140（留余量），待用户确认
```

## 5. Stage 5 配置生成时的校验循环

> SKILL 铁律8 要求"生成即校验"——写一条命令，立刻对照图谱知识表校验，不是写完所有命令再回头核查。
> 按需补取（铁律3）：若发现某命令的 MMLCommand 在 Stage 4 未取，立即回图谱补取，禁止凭记忆生成。

对 LLD 中的每条命令，执行：

```
对每条命令 C（按 task 编排顺序）:
  1. 从 LLD 取该命令的全部参数值
  2. 从 LLD 图谱来源列取该命令的 MMLCommand ID，以及存在时的 AtomTask ID
  3. 对照图谱知识表逐参数校验:
     □ 引用类型: 有 AtomTask 时是否符合其引用约束；无 AtomTask 时是否符合 MMLCommand 已声明约束?
     □ 枚举值: 参数值是否在 MMLCommand CommandParameter 枚举内?
     □ 必填项: 所有 Mandatory 参数是否都已赋值?
     □ 联动关系: 选了A参数则B参数是否已填?
  4. 全部通过 → 写入配置文件
     任一不通过 → STOP, 标注错误, 回 Stage 4 修正 LLD
```

### MMLCommand md 全文必读

每条实际用到的 MMLCommand md 必须**全文读完**（SKILL 铁律11），禁止只读部分字段就生成命令。重点检查：
- 参数是否必填（Mandatory）
- 参数枚举值是否合法
- 参数间联动关系（如选了 A 参数则 B 参数必填）
- 参数引用约束（与 Stage 4 校验表对照）

### 参数约束逐条校验

对照 MMLCommand md 的 CommandParameter，逐参数校验：
- **引用类型**：引用对象是否符合 AtomTask 约束（Stage 4 引用约束校验表）
- **枚举值**：参数值是否在 CommandParameter 列举的合法取值内
- **类型**：参数值类型是否匹配（整数/字符串/IP 等）
- **必填项**：所有 Mandatory 参数是否都已赋值

> 禁止在配置生成阶段凭记忆补充参数——所有参数定义来自 Stage 4 已取齐的 MMLCommand md。若发现 Stage 4 遗漏某条命令的 MMLCommand，必须回退补取（铁律3 按需补取），禁止跳过。

## 6. 通用配置约束（从图谱取）

以下约束不从本文件取，而是从相关 md 的 Rule 段取（SKILL 铁律1）：

| 约束类型 | 来源 |
|---|---|
| 执行时序 | task md 的 Rule 段 / CompoundTask 步骤表 |
| License 前置 | Feature md / License 对象 |
| 对象依赖关系 | AtomTask 约束 / MMLCommand 参数引用 |
| 命令间联动 | AtomTask 配置方法 |
| 跨网元协同 | 方案 md 的协同段 |

> 知识优先级：**场景规则（方案/任务 md 内的 Rule 段）> 图谱对象 Rule 字段 > SKILL 通用约束**
