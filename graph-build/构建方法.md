> 字段和结构以 `对象规范.md` 为准，骨架见 `template/`。本文件讲**怎么想、怎么判断**。

---

## 1. AtomTask（命令级：这条命令有哪些合法配置方法）

**什么时候建**：只为本批编排实际用到的配置类命令建 atom，且以平台上尚不存在为前提（`图谱接口.md` §5）。已存在的 atom，只有当本文档暴露出其字典里缺失的配置方法时才更新（§7）。

**输入**：MMLCommand 全文（`get_md`，**主源**，参数定义以它为准）+ 本文档中该命令的所有语句和数据规划行（佐证）+ 必要时查 Feature 文档中的用例。

**写法**：

1. **配置方法**：按“配置维度”组织成字典。一个维度 = 一个决定配置行为的参数（或一组联动参数），列出各取值的作用、配套必选参数和典型场景。
   - 讲“这条命令有哪些合法的配置方法”，**不逐个特性或运营商罗列取值**，那是 FT / CS 的职责。
   - 不照抄参数表：只挑会改变配置行为的维度；纯标识类参数（名称、索引）在引用约束或约束中说明即可。
   - 文档中出现的用法必须能在字典里找到对应的维度和取值。找不到，说明字典不完整，应补上。
2. **决策点**：从配置维度派生出配置时需要做的选择。命令用法单一时，写明“无分支”。
3. **约束**：从命令 notes 和文档注意事项中梳理，如唯一性、互斥、生效方式、规格上限、执行前置。
4. **引用约束**：逐个检查“名称 / 索引 / 组号”类参数引用的是哪条命令创建的对象（从 CommandParameter 的说明，以及文档中的配置顺序判断）。**这一段是配置生成做参数校验的依据，不能省略。**

不写局点取值；典型取值需要举例时，写平台枚举值或 `<规划值>`。

## 2. 还原语句级时间线（CT / FT / CS 共用的前置步骤）

对每个 D / F 型单元，先从 `corpus.json` 和原文还原出**语句级时间线**，再决定怎么组装。每条语句一行（重复执行的同形语句可以合并为一行，但要写明次数和各次的差异），**不能只写“节选”**：

```markdown
| # | 原文行 | 相位 | 命令 | 对象 / 关键参数 | 条件（逐语句） | 依赖 / 修改的对象 |
|---|---|---|---|---|---|---|
| 1 | L100 | 通道 | SET XXX | P1=A | 无（通用） | — |
| 2 | L101–102 | 通道 | ADD YYY ×2 | 每个实例一条 | 无（通用） | — |
| 3 | L105 | 通道 | ADD YYY | 第 3 个实例 | L104 注释：“以下仅 Z 场景涉及” | — |
| 4 | L106 | 组 | ADD GRPMEM | 成员 = 实例 3 | L104 注释（同上） | 修改 #2 创建的组 |
```

- 条件列按 `语料处理.md` §3.1 的作用域规则逐语句填写；`corpus_summary.md` 的“逐语句作用域”表是起点，要人工确认。
- 条件分支修改无条件部分的对象时（往通用组里追加成员、引用通用对象），在最后一列写明，编排时不能把这类语句从依赖对象中拆开。
- 数据规划表孤立项归入本单元的，也在时间线里占一行（原文行写规划表行号，命令列注明“仅规划表”）。
- 时间线写进 `_work/02-配置单元与映射.md` 对应单元的下方，作为编排与审查的对照基准。编排顺序与时间线不一致的（例如依据特性文档把某步后移），必须在资产中注明“偏离原文顺序”及依据。

## 3. CompoundTask（步骤级：可复用的多命令模块）

### 3.1 何时抽 CT

- 一个步骤包含 **≥3 条不同的配置命令**，且配置目标内聚（完成同一件事）→ CT 候选。
- 少于 3 条不同命令 → 直接引用 AtomTask，不抽 CT（下限，防止过度拆分）。计数时**不含** License 开关（`SET LICENSESWITCH` 等 License 前置命令）：它由 FT / CS 在步骤之前单独编排，也不进 CT 的 `command_set`。
- D 型单元：每个接口 / 对端对接 / 数据块通常就是一个 CT。
- **按复用粒度切**：“对端 Profile + 服务 (+ 订阅)”这类对端 NF 对接会在多个场景中复用，应抽成一个通用 CT，由各场景在「场景差异」中登记自己的用法；不要按场景各建一个。
- **目标内聚**：只把服务于同一个配置目标的命令放进一个 CT。一组互不相关的开关，与其拼成一个“调优大全”CT，不如由 CS 直接引用各 Atom。

### 3.1.1 CT 基线写什么

CT 的 `## 配置方法` 与典型脚本是**基线**，会被多个来源复用，所以：

- 基线只写配置维度和 `<规划值>`；取值只有在它对所有引用方都成立时才写（如 Feature 文档给出的唯一合法值）；
- 来自单一文档（尤其是运营商规范）的具体取值，写进该引用方在「场景差异」中的那一行，或写进 CS 的运营商规范；
- 语义固定的编号（如软参位号 → 功能含义）可以写进基线的说明列，但“要不要置位、置成什么”属于引用方。

### 3.2 复用判定（替代旧规范中的 `_index.md`）

1. 按 `图谱接口.md` §4.6 搜索候选，对前 5 个候选 `get_md`，读取 `command_set`。
2. 计算 Jaccard = |本步骤命令集 ∩ 候选 command_set| / |并集|。
3. 判断**相位同义**，以下三项中满足至少两项即成立：① 配置目标相同；② 操作的对象链相同；③ 共有命令的相对顺序一致。
4. 决策：

| 条件 | 决策 |
|---|---|
| J ≥ 0.75 且相位同义 | **复用**：引用已有 CT；本单元的差异写进该 CT 的「场景差异」（→ 更新该 CT，§7） |
| 0.4 ≤ J < 0.75，或相位只是近义 | **扩展 or 新建**：候选只是缺少少量命令、且语义相同 → 扩展候选（加命令、加场景差异行）；否则新建，共享子 atom |
| J < 0.4，或相位不同 | **新建** |

语义判断优先于 Jaccard：命令集完全相同但配置目标不同（例如同一组命令，一个用于 License 前置，一个用于业务开通）时，**不复用**。

### 3.3 场景差异（防止“假通用”）

每个引用该 CT 的场景（FT 的一种激活方法，或 CS 的一个单元）在「场景差异」表中占一行，写明：执行了哪些命令、省略了哪些命令、相对基线的参数差异（含本场景的具体取值和对象引用方式，如“按索引引用 / 按名称引用”）、对象与步骤位置。**复用时本场景的差异必须写回 CT**，不能只写在引用方。行首用 `[[引用方ID]] / 场景名` 标识（这是正文引用，不是边）。场景的条件（如“仅某专网”）要照时间线逐语句写准，不能把部分语句的条件扩大到整行。

## 4. FeatureTask（特性级：这个特性怎么配）

**前提**：单元映射到 Feature 的证据为强或中，且已在 P3 GATE 中确认。

**输入分工**：

| 输入 | 作用 |
|---|---|
| Feature 文档簇（`get_md` 概述 + 配置相关子文档） | 特性全貌：所有激活方法、对象链、约束、License 前置。**FT 的覆盖面以它为准** |
| 本文档的对应单元 | 本批的一个或多个具体场景；运营商取值**不进 FT** |
| 相关 AtomTask（已有或 P4 新建） | 参数合法性核对 |

**写法**：

1. **配置概览**：对象链 + 激活方法骨架（有几种激活方式，各自的差异维度是什么）。
2. **配置流程**：混合编排，多命令步骤引用 CT，单命令直接引用 Atom：
   ```
   1. **步骤名**（一句话）：`CMD1` + `CMD2` + `CMD3` → [[UNC@CompoundTask@slug]]
      - 关键参数：`P1`=<取值或规划值>
   2. **命令名**（一句话）：`CMD4` → [[UNC@AtomTask@CMD4]]
   ```
3. **激活方法与参数差异**：逐场景表，每种激活方法 / 条件至少一行（列定义见模板）。执行的命令、省略的命令、重复执行和刷新位置都必须能从这张表还原。第一列是激活方法的**名称，在本 FT 内唯一**——CS 按这个名称引用 FT 的某种用法（`对象规范.md` §6）。流程中有“总开关 / 生效”类步骤（打开后业务立即生效）时，在配置流程中标出它的步骤号，便于上层方案把它挪到最后。
4. **参数核对**：对每个“参数=值”，逐项核对 Atom 配置方法和 MMLCommand 定义。结论只能是：`通过` / `冲突，待 Atom 更正` / `版本差异待确认` / `待数据规划补齐`。不得在未核对时写“通过”。
5. **信息受限**：Feature 文档簇和本文档都给不出可还原的命令链时，建 `status: draft`，把配置流程等段标注为“信息不足，未编排”，并列出待补项；不虚构 Atom、CT 或参数。
6. **能力型底座**：没有独立配置命令的被动特性，建 `status: foundation` 骨架，在配置概览中说明依赖于哪些特性。

**已有 FT 时**：先核对它能否还原本文档对应单元的每条语句和“参数=值”（含命令顺序）。能还原 → 不改 FT，只在 CS 中写运营商变种；FT 缺少本文档用到的激活方法、命令或参数维度 → 按 §7 更新 FT（新增激活方法行和步骤）。FT 的步骤顺序与本文档不同，且差异是方案特有的 → 不改 FT，在 CS 编排中按时间线拆分引用（`对象规范.md` §6）。

## 5. BusinessDomain / NetworkScenario

- **优先挂靠**：先读 `get_domains`。已有的 BD 能容纳本业务（语义同属），就挂在它下面；已有的 NS 讲的是同一个业务问题，就把新 CS 挂在它下面。
- **新建 BD / NS** 必须在 P3 GATE 中提出并经确认。BD 讲业务归属（“移动性管理”“漫游”“网络开局”），NS 讲一个业务问题及其边界（“5G SA 异网漫游”），**两者都不写配置**。
- **NS 决策点 = 方案路由表**：`| 业务诉求 / 条件 | 推荐方案 |`，第二列写真实的 `[[ConfigurationSolution@…]]`。新增 CS 时必须在这张表里加一行。
- 一份运营商开局规范若同时覆盖多个业务问题（开局基础配置 + 异网漫游 + 信令风暴防控…），按业务问题拆成多个 NS / CS，而不是做成一个巨大的 CS。拆分方案在 P3 中提出。

## 6. ConfigurationSolution（方案：这个业务怎么配）

CS 是本 skill 的顶层产物：它把 Task 层对象编排成一个可执行的方案，并承载运营商规范。

1. **特性关系矩阵**（必填）：对编排的每个 FeatureTask 标注角色，并说明与核心特性的关系。
   - 核心：方案主体，必配
   - 基础（依赖前提）：核心依赖的底层特性，必配，配置常与核心重叠
   - 维度增强：正交的可选叠加
   - 跨网元对端：另一个网元上的对应特性，两侧同配
   - 二选一：互斥路径，选其一

   两个特性的配置对象高度重合时，注明“重叠，配 X 时已包含，无需另配 Y”。依赖前提特性必须进入矩阵，不能只在约束里提一句。
   方案里没有 F 型单元（纯部署类方案）时，矩阵写“本方案不编排产品特性”。
2. **配置编排**：按执行顺序列出每个单元及其引用的 FT / CT / Atom。这是配置生成确定命令顺序的依据，顺序以语句级时间线为准：
   ```
   1. **License 前置**：[[{nf}@AtomTask@SET LICENSESWITCH]]（开启的 License 清单见运营商规范）
   2. **对端对接**：[[{nf}@CompoundTask@peer-x]]（条件：部署时未完成对接）
   3. **核心特性**：[[{nf}@FeatureTask@CODE]]（激活方法：方法A；省略：步骤 6 → 见第 9 步）
   4. …
   9. **打开总开关**：[[{nf}@AtomTask@SET XXX]]（FT CODE 的步骤 6，后移至最后；依据：…）
   ```
   - 引用 FT 时必须写明**激活方法名**；只用其中部分步骤，或要调整某步的位置时，用 `省略：步骤 n` / `后移：步骤 n → 第 m 步` 写明（语法见 `对象规范.md` §6）。不能只用自然语言写“第 1–5 步”。
   - 同一个 FT 的步骤在原文中被其他单元隔开时（如 FT 的第 1 步在单元 A 之前、第 2 步在单元 A 之后），按时间线拆成两处引用，而不是整块放在一处。
   - 条件分支按时间线逐语句写准：带条件的只是某几条语句时，写成“在第 n 步基础上增量执行 …”，不要把整步都标为条件执行。
3. **各单元变种**：只写本方案相对于标准配置方法的差异或排除项。没有变种就写一句“走标准配置方法”。
4. **跨单元 / 跨网元协同**：先后依赖、需要两端对齐的参数（如本端域名变更后，对端设备上的对应记录也要同步更新）；条件分支对通用对象的修改（往通用组追加成员等）。
5. **运营商规范**（有 `operator` 时必填）：按“强制项 / 推荐值 / 规划规则”三个子节写（来自 `语料处理.md` §6），每一条都注明作用于哪个命令、哪个参数；类别按参数逐个判定。成员与对应关系（组成员、号段 → 取值、按对端的策略）写成清单，不能只写“每组一条”。局点数据脱敏。
   CT 场景差异中本方案那一行写的具体取值，也要在这里出现，保证运营商取值集中在 CS 可查。
6. **额外命令必须进 Task**：CS 中出现的每一条命令，都必须能追溯到某个 Atom / CT / FT；不能只在 CS 的叙述里写出一条命令。
7. **License 码必须来自查询**：CS 中提到的 LKV 码和特性对应关系，必须来自文档原文或 License 对象，不能按命名规律推测。

## 7. 更新平台上已有的对象

1. 用 `get_md` 取全文（最新版本），以它为底稿修改，写入 `assets/` 下的对应路径（同 ID 上传时覆盖）。
2. 只做增补：新增字典维度、场景差异行、激活方法行、`command_set` 中的命令及对应的 `组成` 边、路由表行或下游边。原有内容不删、不改写。如果确实发现原有内容有错误，不在本批直接改，登记到修改清单的“疑似问题”一栏，交给用户决定。
3. 在 `_work/修改清单.md` 中逐条记录：对象 ID → 改动位置 → 改动内容 → 依据单元。
4. 同一个对象在本批中只输出一个最终版本；多个单元都要改同一对象时，合并后再写。
5. **派生文本**（如引子中的“含 N 个场景”这类计数、概览中的清单）随增补同步更新是允许的，但要在修改清单中登记；新写的对象不要在引子里写计数。
6. 更新前后的原文都存进 `_work/`（更新前取自平台，放在 `_work/cache/`），审查时逐一 diff，只允许出现增补和第 5 条中的派生文本改动。
