# 图谱构建 SOP（Task 层 + 业务层）

> **一句话**：把一份文档里的“配置知识”拆成可复用的 Task 层对象，再用业务层方案把它们编排起来；
> 命令层、特性层的事实一律从图谱平台查，本 skill 只负责写 Task 层和业务层。
>
> | 模块 | 何时读 | 承载内容 |
> |---|---|---|
> | `图谱接口.md` | 任何一次图谱调用前 | MCP 调用规则 + 构建场景的查询配方（查命令、LKV→特性、复用候选…） |
> | `语料处理.md` | P1–P2 | 语料画像、配置单元切分、单元分类、实体映射、版本差异处理 |
> | `对象规范.md` | P4–P6 写 md 时 | 6 类对象的 ID / YAML / 正文结构 / 边白名单（**唯一权威**） |
> | `构建方法.md` | P4–P6 | Atom / Compound / FeatureTask / BD / NS / CS 的逐类构建方法与复用判定 |
> | `核查.md` | P7 | 自检清单、闭包校验、独立审查协议、严重级 |
> | `template/` | 写 md 时 | 6 个文件骨架 |
> | `scripts/` | P1、P2、P7、P8 | 语料抽取、参数核对、资产静态检查、打包（Python 3 标准库，无第三方依赖） |

---

## 1. 定位与分工

| 层 | 承载什么 | 本 skill 的动作 |
|---|---|---|
| 命令层 MMLCommand / ConfigObject | 静态：命令原文、参数定义（CommandParameter 权威） | **只读**（get_md），不改、不建 |
| 特性层 Feature / License | 静态：特性原理、激活文档、License | **只读**，不改、不建 |
| Task 层 AtomTask / CompoundTask / FeatureTask | 动态：命令怎么配、多命令步骤怎么组、特性怎么配 | **构建 / 增量更新** |
| 业务层 BD / NS / CS | 编排：业务问题、方案路由、方案怎么配、运营商规范 | **构建 / 增量更新** |

**三条分层纪律**（贯穿全程）：

1. **静态不重复**：参数定义、取值范围、规格不抄进 Task / 业务层，指向命令层、特性层即可。
2. **Task 层保持通用**：Task 层只写与运营商、局点无关的配置方法；具体取值用 `<规划值>` 表达。运营商或局点的硬性要求和推荐值，只进 CS 的 `## 运营商规范` 段。
3. **不回填反向边**：Task 层对象不写 `被引用于`；新建 FT / CS 时，不为了补反向关系去修改被引用的 Task，反向关系由平台 `in_edges` 反查。唯一的例外是业务层包含树：新增 NS / CS 时，必须同步更新上级 BD 的 `下游场景`、NS 的 `下游方案`，因为配置生成是自顶向下导航的（见 `对象规范.md` §4）。

## 2. 铁律（违反任何一条 = 产物不可交付）

1. **【图谱查询只走 MCP】** 命令、特性、License、已有 Task / 业务对象，都必须通过 Graph MCP 查询（`图谱接口.md`）。MCP 不可用时立即停止并报告，不凭记忆补写，不读本地旧资产目录替代。
2. **【不臆造】** 文档和图谱里都没有依据的命令、参数、取值、特性码、License、执行顺序，一律不写。推断出来的内容必须标“推断/待确认”。
3. **【参数以 CommandParameter 为准】** 每个写进资产的“参数 = 值”，都必须到对应 MMLCommand 的参数定义里核对参数名、取值和必选性（用 `check_params.py` 做机械比对）。核对不通过时，只有能确定是同一取值的不同写法（如大小写不同、下划线有无）才可以规范化，并注明“文档写法 X”；其他情况一律标“冲突 / 版本差异待确认”，不自行改值。
4. **【时序与条件不可泛化】** 文档里的命令顺序、重复执行、分支条件、生效 / 刷新位置原样保留，不按经验重排、不合并。条件（含注释型条件，如“以下仅 X 场景涉及”）要**逐语句**还原作用域：它限定哪几条语句，就只限定哪几条。
5. **【调测剥离】** 编排只包含配置类命令（`ADD/MOD/SET/RMV/DEL/LOD` 及持久化类）；`DSP/LST/EXP` 等查询、调测、探测命令和 GUI 操作不进入编排，只在约束或前置检查里用文字说明。
6. **【闭包】** 文档中每条配置类语句**和每行数据规划**，要么在产出资产中能还原，要么在“未入图清单”里写明理由。**静默丢失 = CRITICAL**（`核查.md` §3）。
7. **【先复用后新建】** 新建任何 Task 或业务对象之前，必须先在平台上查同类对象（`图谱接口.md` §5）。能复用就复用；复用前要核对它能否还原本文档的用法，不能就输出更新版；不另起炉灶造重复对象。
8. **【改既有对象须保全原文】** 更新平台上已有对象时，必须先 `get_md` 取全文，在原文上增补，不得删除或改写与本批无关的内容，并在“修改清单”中逐项列出改动。
9. **【GATE 必停】** P3 构建计划必须交用户确认后才能落盘写资产；用户未确认的映射、新建 BD/NS、运营商规范的归属、文档内冲突的取舍，一律不写。
10. **【不自审】** P7 自检之后必须经过独立审查（`核查.md` §4），CRITICAL / HIGH 清零后才算交付。

## 3. 流程总览

```
P0 准备 ─▶ P1 语料画像与切分 ─▶ P2 图谱映射与核对 ─▶ P3 构建计划 ══GATE══▶
P4 AtomTask ─▶ P5 CompoundTask + FeatureTask ─▶ P6 业务层 ─▶ P7 核查 ─▶ P8 打包与报告
```

各阶段的产出物都写进工作目录 `_work/`，后一阶段只使用前一阶段的产出物（管道式）。

### 工作目录

```
{输出根}/{batch}/
├── _work/                       过程产物（不上传）
│   ├── corpus.json              P1 脚本抽取结果
│   ├── corpus_summary.md        P1 汇总：按章节的命令 / License、条件作用域、规划表孤立项、解析异常
│   ├── 01-语料画像.md            P1
│   ├── 02-配置单元与映射.md       P1–P2：单元表、语句级时间线、映射证据、复用记录、版本差异、文档内冲突
│   ├── cache/                   P2 get_md 原文缓存：本批用到的 MMLCommand + 被复用 / 被更新的平台 Task 对象
│   │   └── _not_found.txt       get_md 返回 OBJECT_NOT_FOUND 的 ID
│   ├── 参数核对.md               P2 / P7：check_params.py 产出
│   ├── 03-构建计划.md            P3（GATE 确认的对象与决策）
│   ├── 未入图清单.md             P4–P6 持续追加（lint 闭包读取，格式见 核查.md §1）
│   ├── 修改清单.md               对平台既有对象的改动记录
│   ├── lint_report.md / external_refs.txt   P7 lint 产出
│   ├── 04-核查报告.md            P7（含独立审查结论）
│   └── 05-构建报告.md            P8
├── assets/                      上传资产（目录布局与平台一致）
│   ├── AtomTask/{nf}/{id}.md

│   ├── FeatureTask/{nf}/{id}.md
```

`{batch}` 用“语料简称-日期”。`{输出根}` 默认为当前工作目录下的 `graph-build-output/`。本批只处理文档的一部分时，确定**本批章节范围**（如 `5.8.6`），后面各脚本的 `--scope` 都用它。

## 4. 阶段细则

### P0 准备

1. 确认 MCP 可用：调用一次 `get_domains`，同时拿到全部业务域（P2、P6 都要用）。失败则按铁律 1 停止。
2. 确认输入文档路径、目标网元（文档自述或用户指定；以平台 `search_graph` 返回的 `facets.nfs` 为准）、本批章节范围。
3. 建工作目录。

### P1 语料画像与切分（读 `语料处理.md` §1–§3）

1. 运行 `python scripts/extract_corpus.py <文档.md> -o _work/`，得到 `corpus.json` 和 `corpus_summary.md`：章节树、MML 语句（命令 + 参数=值 + 注释 + 生效的条件注释）、数据规划表、LKV 码，以及三张待处理清单——**条件作用域**、**规划表孤立项**（规划表有、配置语句没有的命令 / 参数）、**解析异常**。脚本不可用时按 `语料处理.md` §2 手工抽取，产出同样的内容。
2. 通读文档（至少通读目录和各章首尾，本批范围内的章节全读，**包括数据规划表**），写 `01-语料画像.md`。
3. 把本批范围切成**配置单元**并分类（F / D / N，判据见下表）；为每个 D / F 单元写**语句级时间线**（`构建方法.md` §2），条件列逐语句填写。
4. 逐项处理 summary 中的三张清单：孤立项要归入某个单元，或列为待决事项；解析异常登记为文档缺陷。

| 单元类 | 判据 | 落到 |
|---|---|---|
| **F 型**（特性配置） | 能映射到平台上一个 Feature（有 LKV、特性名或命令指纹证据） | FeatureTask（+ CompoundTask） |
| **D 型**（部署 / 基础配置） | 有配置命令，但不属于任何产品特性：接口对接、本局数据、软参、平台可靠性、对端 NF 对接 | CompoundTask；不足 3 条不同命令的直接用 AtomTask |
| **N 型**（非配置） | 原理、组网说明、GUI 操作、查询 / 调测、回退脚本、参考信息 | 不建 Task；有价值的约束写进 CS，其余记“未入图清单” |

### P2 图谱映射与核对（读 `语料处理.md` §4–§6、`图谱接口.md` §4–§6）

对每个单元查询平台，填入 `02-配置单元与映射.md`：

1. **取命令定义并缓存**：对本批语句和规划表中出现的每条配置类命令 `get_md` 其 MMLCommand（默认取最新版本），把返回的 `md` 原样存入 `_work/cache/`，`OBJECT_NOT_FOUND` 的 ID 写入 `cache/_not_found.txt`。
2. **参数核对**：运行 `python scripts/check_params.py <batch>/ --scope <本批章节>`，把 `参数核对.md` 的每一项转成版本差异表或文档内冲突表中的一行，并给出处理方式（`语料处理.md` §5）。
3. **特性映射**（F / D 判定依据）：按信号强度依次使用 LKV → License → `对应特性`、章节标题或特性名搜索、命令指纹（`search_graph` 查 Feature 正文；命中子文档时回溯到概述），每条映射都记录证据及其强度（强 / 中 / 弱）。只有弱证据的映射必须标“待确认”。
4. **已有 Task**：查每条命令的 AtomTask、每个候选步骤的 CompoundTask、每个映射特性的 FeatureTask 是否已存在。每个 CT 候选单元都写一条**复用记录**（查询词 / 候选 / Jaccard / 相位判断 / 结论）。拟复用或拟更新的既有对象也存入 `_work/cache/`，并逐一核对它能否还原本文档对应的“参数=值”和步骤；不能还原的，改列为“更新”。
5. **已有业务层**：从 `get_domains` 结果和 `search_graph(layer=业务层)` 找可挂靠的 BD / NS / CS。

### P3 构建计划 ══ GATE ══

写 `03-构建计划.md`，展示给用户后 **STOP**，等待确认。计划必须包含：

1. 单元清单：单元 → 分类 → 落到哪些对象；N 型单元不入图的理由。
2. 对象清单，分**新建 / 更新（平台既有）/ 复用（不改）**三栏，每个对象写明 ID 和依据的单元。
3. 特性映射表：单元 → Feature ID → 证据强度；标“待确认”的映射逐条列出。
4. 业务层建模：挂靠哪个 BD / NS（已有或新建），CS 的 ID，运营商规范收录哪些条目。
5. 版本差异表、文档内冲突表、规划表孤立项的处理方案。
6. 批次划分：单批超过约 40 条配置类命令时，按单元分批，本批只做第一批。

需要用户决定的事项逐条列出：是什么、**原文依据（行号 + 原文摘录）**、为什么需要用户定、有哪些选项、不定的后果。决策前提必须能对照原文核实，不能只写自己的概括。

### P4 AtomTask（读 `构建方法.md` §1）

按确认后的计划，对编排中用到、且平台上缺失（或需要补充）的配置类命令逐条建 AtomTask：以 MMLCommand 全文为主源，以文档用法为佐证。**不为编排用不到的命令建 atom。**

### P5 CompoundTask + FeatureTask（读 `构建方法.md` §2–§4）

1. D 型单元：按语句级时间线 → 复用判定 → 新建、扩展或复用 CompoundTask。CT 的基线只写维度和 `<规划值>`，单一来源的具体取值写进引用方的场景差异行或 CS。
2. F 型单元：以 Feature 文档簇（get_md 概述 + 子文档）为特性全貌，以本文档为本批场景，新建或更新 FeatureTask；需要抽出的多命令步骤建为 CompoundTask。激活方法表的每一行都要有唯一名称，供 CS 引用。
3. 参数核对：每条“参数=值”都与 AtomTask 配置方法、MMLCommand 参数定义三方核对，结论与 `参数核对.md` 一致。

### P6 业务层（读 `构建方法.md` §5–§7）

1. BD / NS：优先挂靠已有对象；需要新建或更新时按模板写。更新已有 NS 时，要把新 CS 加入其决策点路由表和 `下游方案` 边。
2. CS：先写特性关系矩阵，再写配置编排（引用 FT 的部分步骤时按 `对象规范.md` §6 的写法）、跨单元协同、运营商规范、决策点和约束。

### P7 核查（读 `核查.md`）

1. 运行 `python scripts/lint_assets.py <batch>/ --corpus <batch>/_work/corpus.json --scope <本批章节>`：检查结构、边白名单、命令闭包与参数闭包（语句 + 规划表），并产出 `external_refs.txt`。报告会记录完整命令行，供审查复现。
2. 把 `external_refs.txt` 中的 ID 分批 `get_md` 确认在平台上存在；不存在的即为断链，必须修复。
3. 重跑 `check_params.py`，确认每一项都已在资产或未入图清单中处理。
4. 按 `核查.md` §2 做人工自检。
5. 独立审查（`核查.md` §4）：CRITICAL / HIGH 全部修复并复审通过后，写 `04-核查报告.md`。审查发现计划前提有误时，回到 P3 重新请用户确认。

### P8 打包与报告

1. 运行 `python scripts/pack_bundle.py <batch>/`，生成 `{batch}.zip`（只含 `assets/` 下的 md）。
2. 写 `05-构建报告.md`：对象统计（新建 / 更新 / 复用）、实际使用的平台版本、修改清单、未入图清单、版本差异、文档内冲突、待确认事项、上传说明。
3. 告诉用户：通过平台「上传」页上传 zip（导入时按 frontmatter 归类：同 ID 覆盖、新 ID 新增），上传后用 `get_md` 抽查。新对象的 `status` 为 `draft`，升为 `active` 需要人工审阅。

## 5. 交互规则

- P3 GATE 是强制停点；P4–P7 过程中发现计划外的重大问题（如映射被证伪、计划前提与原文不符、需要新建计划外的 BD），暂停并请用户确认。
- 用表格展示，追问时说明原因和影响，并附原文行号；用户可以随时要求“缩小范围 / 换批次 / 到此为止”。
- 过程日志统一加前缀：`[图谱]` 表示 MCP 调用及结论，`[构建]` 表示写入资产，`[核查]` 表示检查结果。
