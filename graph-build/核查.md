# 核查（P7）

> 三道关：① 脚本静态检查（结构 + 闭包）；② 构建者自检；③ 独立审查（**不能由构建者自己担任**）。
> 脚本通过只说明结构合格。**脚本不报错不代表内容正确，脚本报错则一定有问题**。参数语义、时序、分支必须经过人工审查。

---

## 1. 脚本检查

```
python scripts/lint_assets.py <batch>/ --corpus <batch>/_work/corpus.json --scope <本批章节>
python scripts/check_params.py <batch>/ --scope <本批章节>
```

只处理文档一部分时**必须带 `--scope`**，否则全文其他章节会被计入闭包。两份报告都会记录实际命令行，审查者照此复现。

脚本检查的内容：

| 检查 | 级别 |
|---|---|
| YAML 必填字段、`type` 与 ID 一致、ID 段数、文件名 = ID、存储路径 | CRITICAL |
| Task / 业务层出现了 `version` / `source` / `source_evidence_ids` / `## 证据` | CRITICAL |
| `## 边` 缺失、不是最后一段、关系名或目标类型不在白名单中、指向禁用类型 | CRITICAL |
| 残留 `{{…}}` 模板占位 | CRITICAL |
| CT 的 `command_set` 与 `组成` 边不一致；Atom 的 `ref` 与 `对应命令` 不一致 | CRITICAL |
| 必备正文段缺失（按 `对象规范.md` §5） | HIGH |
| 业务层 `domain` / `scenario` 与 ID、路径不一致 | CRITICAL |
| 新写了 `被引用于` 边 | WARNING（已取消回填；如属既有对象的原文则忽略） |
| **命令闭包**：范围内配置语句和**数据规划表行**中的命令，没有落到任何 Task（被 `[[..@AtomTask@CMD]]` 引用、是本批 atom、或在 CT `command_set` 中；被引用且已缓存的平台既有 Task 同样计入），也没有在未入图清单行首登记 | CRITICAL |
| **参数闭包**：范围内语句 / 规划表中的参数名没有出现在任何资产中，也没有以 `- 参数` / `- 局点数据` 条目登记 | WARNING（须逐条人工确认） |
| CS 配置编排引用 FT 未写「激活方法」，或激活方法名在 FT 中不存在 | HIGH |
| 编排或配置方法中出现查询 / 调测类命令（`DSP/LST/EXP`…） | HIGH |

`_work/未入图清单.md` 的格式（lint 据此判断闭包排除项）：

```markdown
# 未入图清单
- 章节: 3.4 （回退脚本，N 型，不编排）              ← 整节排除：按标题编号或完整标题匹配，含其子节
- 章节: 5.7 （测试场景配置，用户在 P3 决定不入图）
- SET XYZ：版本差异，平台无此命令，P3 用户决定放弃   ← 单命令排除：命令名写在行首
- 参数 SET ABC.PARAM1：版本差异，平台无此参数          ← 参数级排除
- 局点数据：ADD PEER.IPADDR, ADD PEER.FQDN（已脱敏）  ← 脱敏参数批量登记
```

每一项都必须写明理由。只有 N 型章节、用户在 P3 明确放弃的内容、版本差异导致无法入图的命令，才能进入这份清单。

脚本还会生成 `_work/external_refs.txt`：所有被引用、但不在本批 assets 中的 ID。**必须逐批 `get_md` 确认它们在平台上存在**，不存在的就是断链（CRITICAL）。

## 2. 构建者自检

| 维度 | 检查点 |
|---|---|
| 静态不重复 | Atom 没有照抄参数表或规格；CS 没有复述 FT 的内部步骤 |
| Task 通用性 | Task 层没有局点 IP / 实例名 / 运营商专属取值；这些只出现在 CS 的运营商规范中（且已脱敏） |
| 参数合法 | 每个“参数=值”都核对过 CommandParameter；核对结论如实填写（`构建方法.md` §4） |
| 时间线保真 | FT / CT / CS 的顺序、重复次数、分支、跳过条件与 `02-配置单元与映射.md` 中的时间线一致 |
| 复用 | 每个新建的 CT 都有复用记录（查询词 / 候选 / J / 相位）；复用的 CT 已回填场景差异 |
| 复用对象覆盖 | 每个“复用（不改）”的既有 Atom / CT / FT 都核对过：能还原本文档的每个“参数=值”、步骤与顺序；不能的已改为“更新” |
| 条件作用域 | 时间线逐语句标注条件；条件只落在它限定的语句上，没有扩大到整步 / 整节；条件分支对通用对象的修改已写明 |
| 规划表与文档内冲突 | `corpus_summary` 中的规划表孤立项、解析异常逐项有处理结论；文档内冲突表已填写，并在 P3 中请用户确认过涉及范围的冲突 |
| CT 基线 | CT 基线只含维度与 `<规划值>`；单一来源的取值在场景差异 / CS 中 |
| 引用约束 | 新建或更新的 Atom 都有 `### 引用约束` 段 |
| 业务包含树 | 新 NS 已加入 BD 的 `下游场景`；新 CS 已加入 NS 的 `下游方案` 和路由表 |
| 修改保全 | 所有更新的既有对象，与平台原文比较只有增补；修改清单已完整登记 |
| 映射真实 | FT 对应的 Feature、CS 中出现的 LKV 码都来自查询结果，证据已记录在映射表中 |
| 未入图有据 | `未入图清单.md` 中每一项都写明了理由（N 型 / 版本差异 / 用户决定放弃 …） |

## 3. 闭包校验（人工部分）

- **B1 命令闭包**：每个单元的配置类命令 ⊆ {FT / CT 编排的命令 ∪ 场景差异中的省略项 ∪ 未入图清单}。脚本只能检查命令名是否出现，“出现在正确的位置”需要人工核对。
- **B2 参数闭包**：文档中每个与行为相关的“参数=值”，要么进入 Task 的配置方法 / 场景差异 / 参数核对，要么进入 CS 的运营商规范，要么在未入图清单中说明（纯局点标识数据可以批量说明，如“SEPP 实例名、IP 属于局点数据，已脱敏”）。静默丢失 = CRITICAL。
- **B3 反向追溯**：资产中每个“参数=值”都能追溯到文档某一行，或者 Feature 文档簇、MMLCommand 定义。无来源的取值 = CRITICAL。
- **B4 信息源边界**：FT 如果声明只覆盖了 Feature 文档簇的一部分，必须逐一列出排除的子文档并说明理由。静默排除了含配置命令的子文档 = CRITICAL。

## 4. 独立审查协议

- **审查者**：独立的子 Agent，**不修改任何资产**。运行环境不支持子 Agent 时，以一轮独立的“审查者”角色执行，并在核查报告中注明“非独立审查”，提醒用户人工复核。
- **审查者的输入**：原文档、`_work/` 下的全部过程文件、`assets/` 下的全部资产，以及 MCP 访问权限（用于核对命令、特性和既有对象）。
- **审查方法**：先照报告中记录的命令行重跑 `lint_assets.py` 和 `check_params.py`；逐个单元把原文与资产对照；抽查（至少每类对象各 2 个，CS 全审）参数值、顺序和分支；重新做一遍映射证据最弱的那些映射；核对修改清单中的对象与平台原文的差异。
- **审查立场**：默认产物有问题，只认证据；每个问题都要定位到“对象 ID + 规则”。

**严重级**：

| 级别 | 含义 | 例 |
|---|---|---|
| CRITICAL | 会导致生成错误配置，或图谱结构断裂 | 静默丢失命令或参数；臆造取值；断链；错误的特性映射；删改了既有内容 |
| HIGH | 知识不完整或会误导使用方 | 缺少引用约束；场景差异没有回填；时间线顺序被改动；运营商取值进入了 Task |
| MEDIUM | 质量问题 | 决策点影响写得不全；约束缺少严重级；命名不规范 |
| INFO | 建议 | — |

CRITICAL 或 HIGH 不为 0 → 退回构建者修复 → 复审。全部清零后写入 `04-核查报告.md`：`{结论, 问题清单[{对象, 规则, 级别, 状态}], 审查方式（独立 / 非独立）}`。
