# 对象规范（6 类对象的唯一权威）

> 本文件取代旧规范中的 `task/字段定义.md`、`business/字段定义.md`、`图谱边定义.md` Task 层 / 业务层部分，以及 `conventions/命名规范-建议.md` 中与这两层相关的内容。
> 与平台 `default_registry.yaml` 对齐：Task 层 `scope: task`（3 段 ID，无版本）；业务层 `scope: cross`（2 段 ID，`path_fields: domain[, scenario]`）。

---

## 1. 通用约定

- **一个 md = 一个对象**，结构固定为：YAML frontmatter → `# 标题` + `> 引子` → 内容段 → `## 边`（**必须是最后一段，且单独成行作为标题**，否则平台不解析边）。
- **文件名 = 完整 ID + `.md`**，不做任何字符替换（保留空格和 `@`）。
- **引用** 一律使用裸 wikilink `[[逻辑ID]]`：不带路径、不带 `.md`、不用别名，也不引用 md 内部的章节锚点（引用粒度是整个 md）。因此决策点和约束**不编号**。
- **无版本**：Task 层和业务层都不写 `version`（不进 ID，不进 YAML，也不进路径）。它们引用的命令和特性有版本，由使用方按目标环境选择；本批构建时实际查询的版本记录在构建报告里。
- **无证据段**：不写 `source` / `source_evidence_ids`，不设 `## 证据` 段。可追溯性由 `_work/` 过程文件承担；CS 可以在引子中用一句话写明依据的文档名和版本。
- **不留占位**：交付物中不得残留 `{{…}}` 模板占位，也不得有 `[[...]]` 空引用。`<规划值>` / `<SEPP 实例名>` 这类尖括号取值占位是**有意表达**，允许使用。
- **status**：新建一律 `draft`；升为 `active` 由人工审阅决定，本 skill 不做。更新既有对象时保留其原 status；若本批改动较大，在修改清单里提示“建议复审”。FeatureTask 另有 `foundation`（能力型底座，无独立配置）。
- **未知字段保留**：更新既有对象时，原 YAML 中本规范未列出的字段原样保留。

## 2. ID 与命名

| 类型 | ID | local / slug 规则 | 存储路径（assets/ 下） |
|---|---|---|---|
| AtomTask | `{nf}@AtomTask@{命令名}` | 命令名原样（含空格），1:1 对应命令 | `AtomTask/{nf}/` |
| CompoundTask | `{nf}@CompoundTask@{slug}` | 小写 kebab-case 英文**语义名**（如 `sepp-peering`、`n2-sctp-ngap`），定下后不再改 | `CompoundTask/{nf}/` |
| FeatureTask | `{nf}@FeatureTask@{feature_code}` | 特性码原样，1:1 对应特性 | `FeatureTask/{nf}/` |
| BusinessDomain | `BusinessDomain@{domain}` | kebab-case | `Business/{domain}/` |
| NetworkScenario | `NetworkScenario@{scenario}` | kebab-case | `Business/{domain}/{scenario}/` |
| ConfigurationSolution | `ConfigurationSolution@{scenario}-{solution}` | 以 scenario 开头；运营商方案用 `{scenario}-{operator}[-{variant}]`（如 `inter-plmn-roaming-cmcc`） | `Business/{domain}/{scenario}/` |

- `nf` 取平台上的网元名（`UNC` / `UDG`），以查询结果的 `nf` 字段为准。
- 运营商 slug 用通用缩写：`cmcc`（中国移动）、`ctcc`（中国电信）、`cucc`（中国联通）等。
- CompoundTask 命名讲它**做什么**，不讲它用在哪个特性里（`peer-nf-profile`，而不是 `lcs-step2`）。

## 3. YAML 字段

| 字段 | Atom | Compound | FeatureTask | BD | NS | CS | 规则 |
|---|---|---|---|---|---|---|---|
| `id` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | 与文件名一致 |
| `type` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | 与 ID 中的 Type 段一致 |
| `name` | 命令名 | slug | feature_code | 中文名 | 中文名 | 中文名 | |
| `name_zh` | 配置动作名（= H1 中的动作名） | 步骤中文名 | 特性名 | 同 name | 同 name | 同 name | |
| `nf` | ✅ | ✅ | ✅ | — | — | — | |
| `ref` | `{nf}@MMLCommand@{命令}` | —（不写或写 null） | `{nf}@Feature@{code}` | — | — | — | 必须指向平台上存在的对象 |
| `command_set` | — | ✅ | — | — | — | — | 见下 |
| `domain` | — | — | — | ✅ 自身 | ✅ 所属 BD | ✅ 所属 BD | 与路径段、ID 一致 |
| `scenario` | — | — | — | — | ✅ 自身 | ✅ 所属 NS | CS 的 ID 必须以它开头 |
| `operator` | — | — | — | — | — | 可选 | 运营商方案必填，值为运营商 slug |
| `status` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | `draft` / `active` / `stale`（FT 另有 `foundation`） |

**`command_set`**：本 CT 在 `## 配置方法` 步骤表中**直接编排**的配置类命令名列表（= `组成` 边所指 atom 的命令名集合）。不含前置依赖命令，也不含被本 CT 以 `引用步骤` 引入的其他 CT 的命令。它是复用判定（Jaccard）和检索的核心字段。

## 4. 边（`## 边` 白名单）

格式：`- 关系: [[ID]]`，一行可以写多个目标（`- 组成: [[A]], [[B]]`）。

| 源类型 | 关系 | 目标类型 | 基数 |
|---|---|---|---|
| AtomTask | 对应命令 | MMLCommand | 恰好 1 个（= ref） |
| CompoundTask | 组成 | AtomTask | ≥1（与 command_set 一一对应） |
| CompoundTask | 引用步骤 | CompoundTask | 可选（嵌套一个完整的子步骤时使用） |
| FeatureTask | 对应特性 | Feature | 恰好 1 个（= ref） |
| FeatureTask | 编排 | CompoundTask / AtomTask | `foundation` / 信息受限的 `draft` 可以为空 |
| BusinessDomain | 下游场景 | NetworkScenario | ≥1 |
| NetworkScenario | 上游域 | BusinessDomain | 恰好 1 个 |
| NetworkScenario | 下游方案 | ConfigurationSolution | ≥0 |
| ConfigurationSolution | 上游场景 | NetworkScenario | 恰好 1 个 |
| ConfigurationSolution | 编排特性 | FeatureTask | 可选 |
| ConfigurationSolution | 复用步骤 | CompoundTask | 可选 |
| ConfigurationSolution | 复用命令 | AtomTask | 可选 |

- **禁止的目标**：ConfigObject、License、CommandParameter（任何源类型都不能指向）；CS 不直连 Feature 或 MMLCommand（通过 FT / Atom 间接关联）。正文中出于说明需要可以写 `[[UNC@Feature@…]]`、`[[UNC@MMLCommand@…]]` 作为跳转引用，这不算边。
- **不写 `被引用于`**：Task 层的反向关系由平台反查（`in_edges`）。更新平台上既有对象时，**原有的 `被引用于` 行原样保留**（不增不删），新增的引用关系不再回填。
- **业务层包含树必须闭合**：新增 NS → 更新所属 BD 的 `下游场景`；新增 CS → 更新所属 NS 的 `下游方案` 和决策点路由表。这两处会被自顶向下导航使用，**不能依赖反查**。
- 旧规范中的细分标签（`编排 compound`、`编排 atom`、`直接引用 atom`）不再使用，统一写 `编排`；平台对任意关系名都能解析，老数据不必迁移。
- 旧规范中 CompoundTask 的 `上游` / `下游` 边不再新建：步骤间的先后顺序由 FT / CS 的编排顺序表达。老数据中已有的保留。

## 5. 正文结构

每类对象的必备段（顺序固定；可以增加子节，但不能缺少或改名，因为下游 `config-generation` 按段名读取）：

| 类型 | 必备段 |
|---|---|
| AtomTask | `# {配置动作名}（{命令}）` + 引子 → `## 配置方法` → `## 决策点` → `## 约束`（含 `### 引用约束`）→ `## 边` |
| CompoundTask | `# {步骤中文名}` + 引子 → `## 配置方法`（步骤表 + 典型脚本 + 步骤位置）→ `## 场景差异` → `## 决策点` → `## 约束` → `## 边` |
| FeatureTask | `# {特性名}（{code}）` + 引子 → `## 配置概览` → `## 配置流程` → `## 激活方法与参数差异` → `## 参数核对` → `## 决策点` → `## 约束` → `## 边` |
| BD | `# {域名}` + 引子 → `## 概览` → `## 范围与边界` → [`## 决策点`] → [`## 约束`] → `## 边` |
| NS | `# {场景名}` + 引子 → `## 概览` → `## 边界` → `## 决策点`（方案路由表）→ [`## 约束`] → `## 边` |
| CS | `# {方案名}` + 引子 → `## 概览` → `## 配置与协同`（特性关系矩阵 + 配置编排 + 各单元变种 + 协同）→ [`## 运营商规范`] → `## 决策点` → `## 约束` → `## 边` |

方括号表示可选；CS 带 `operator` 字段时，`## 运营商规范` 为必备段。

**决策点**：用表格 `| 选项/场景 | 影响 |`，每个选项的影响都要写全；多个相互独立的决策维度分成多个 `### DPn：名称` 子节。没有分支时明确写“本 X 用法单一，无分支”，不能留空。

**约束**：`- **规则名**（critical|warning|info）：约束内容 — 违反后果`。没有约束时明确写“无特殊约束”。

**Atom 的 `### 引用约束`**：`| 参数 | 只能引用 | 说明 |`，写明哪些参数必须引用由哪条命令创建的对象（如 `SCTPGROUPID` 只能引用 `ADD SCTPLEGRP` 创建的组）。这是配置生成做参数引用校验的依据。没有引用型参数时明确写“本命令无引用型参数”。

推断出来的引用关系（命令定义没有声明、依据文档取值关联和配置顺序得出的）要在说明列标“推断”。

**引子不写计数**：引子只写一句定义和上级归属，不写“含 N 个场景 / 方案”这类会随增量更新过期的数字。

## 6. CS 配置编排行的语法

CS 的 `### 配置编排` 是有序列表，每行一个编排单元。配置生成按下面的约定展开：

```
n. **单元名**：[[目标ID]]（修饰1；修饰2；…）
```

| 修饰 | 适用目标 | 含义 |
|---|---|---|
| `条件：…` | 任意 | 执行条件；不满足时跳过本行。条件只作用于本行 |
| `激活方法：<名称>` | FeatureTask | 按 FT「激活方法与参数差异」中该名称的行展开（**引用 FT 时必填**） |
| `省略：步骤 a, b` | FeatureTask / CompoundTask | 展开时跳过这些步骤（步骤号即 FT 配置流程 / CT 步骤表的序号） |
| `后移：步骤 a → 第 m 行` | FeatureTask | 步骤 a 不在此处执行，改在本编排的第 m 行执行；第 m 行要写 `（[[FT]] 的步骤 a）` |
| `仅步骤：a–b` | FeatureTask / CompoundTask | 只展开这些步骤；同一个 FT 被拆成几处引用时使用 |
| `重复：按 <维度>` | 任意 | 按某维度（如每个伙伴、每个对端）重复执行本行 |
| `增量：在第 n 行基础上` | 任意 | 本行是第 n 行的条件增量（只多执行若干语句 / 追加成员），不是另一套配置 |

规则：

- 同一个 FT 的所有引用行合起来，必须覆盖它在所选激活方法下的全部步骤（每一步或被执行，或被显式 `省略`）。
- 被 `省略` 的步骤如果对方案仍然必要，必须在别处引用（通常配合 `后移`）。
- CS 中的每个 `[[FT]]` 都要出现在「编排特性」边中，每个 `[[CT]]` / `[[Atom]]` 也要出现在「复用步骤 / 复用命令」边中（边只表达“用到了”，顺序和修饰以编排列表为准）。
