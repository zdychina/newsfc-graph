# 语料处理（P1–P2）

> 用户提供的文档格式不统一。本文件给出**框架 + 判据**，Agent 根据每份文档的实际结构来应用，而不是套固定流水线。
> 所有结论写进 `_work/01-语料画像.md` 和 `_work/02-配置单元与映射.md`。

---

## 1. 语料画像（01-语料画像.md）

读目录和各章首尾，回答下面这些问题：

| 维度 | 要回答的问题 |
|---|---|
| 语料类型 | 运营商配置规范 / 产品配置指导书 / 业务专题 / 方案文档 / 割接方案 / 其他 |
| 适用对象 | 哪个网元（AMF、SMF → UNC；UPF → UDG）、哪个产品版本、哪个运营商或局点 |
| 映射信号 | 是否有特性码（`[A-Z]{2,5}FD-\d{6}`）、LKV License 码、特性名、命令以什么形式出现（代码块 / 表格 / 正文） |
| 取值性质 | 参数值是**示例**、**规划规则**（如 FQDN 命名格式），还是**强制要求**（“必须 / 需要开启 / 要求”） |
| 范围 | 覆盖哪些大块（组网、License、本局数据、接口、特性、可靠性…）；哪些章节没有配置命令 |
| 不确定点 | 文档自相矛盾、疑似笔误、引用了外部文档（如《xx 规划原则》）而本文未给出内容 |

> 例：《中国移动 AMF 异网漫游配置规范（20.13.2）》= 运营商新建设备配置规范；网元为 UNC（AMF）；版本 20.13.2；无特性码；有 LKV 码（§5.1 的 License 开关清单、§5.8.6.1 漫游 License）；命令全部在代码块中，并配有数据规划表；取值多为中国移动的规划值，含 IP、实例名等局点数据；§3 组网、§4 License GUI 激活、§7 参考信息中基本没有 MML 配置。

## 2. 语料抽取（scripts/extract_corpus.py）

```
python scripts/extract_corpus.py "<文档.md>" -o <batch>/_work/
```

产出：

- `corpus.json`：章节树；每个章节包含 `statements`（MML 语句：`verb`、`command`、`params{名:值}`、前一行的 `//` 注释、`conditions`（生效的条件注释）、行号、`anomalies`（解析异常）、`inline`（位于代码块外））、`plans`（数据规划表中的“命令 / 参数 / 取值样例”）、`licenses`（LKV 码）、`mentions`（正文中提到但不在代码块里的命令）、`conditions`（正文中的条件描述）。全局另有 `orphan_plans`（规划表孤立项）和 `anomalies`。
- `corpus_summary.md`：按章节的命令 / License 汇总，外加四张待处理清单：
  1. **条件注释与逐语句作用域**：每条受条件注释约束的语句，及其生效的注释（行号 + 内容）；
  2. **正文中的条件描述**：章节级的“按需 / 当前不用配置 / 仅 X 场景”等表述；
  3. **规划表孤立项**：数据规划表里有、配置语句里没有的命令（类型=命令），或命令出现过、但该参数从未被任何语句用到的规划变体（类型=参数）；
  4. **解析异常**：无法解析的参数片段、参数名不合法、取值带首尾空白、参数重复。

脚本只做**确定性抽取**，不做语义判断。四张清单都必须在 P1–P2 逐项处理（归入单元、登记为文档缺陷或冲突、列为待决事项），不能跳过。另外要人工复核：

- 语句跨行、缺少结尾 `;`、中英文标点混用（缺 `;` 的语句标 `unterminated`）；位于代码块外的语句（多为围栏缺失或错位）；
- 参数值中含逗号或引号嵌套；
- 表格中一行写了多条命令（`ADD X<br>ADD Y`）。

脚本不可用时手工抽取，产出同样的内容，不能省略这一步：闭包校验依赖它。

## 3. 配置单元切分、分类与条件作用域

**配置单元** = 一个完整的配置目标，通常对应一个含配置命令的章节（最小到三级或四级标题）。切分规则：

1. 同一目标的“数据规划 + 配置步骤”属于**同一个单元**。数据规划表常常还包含配置步骤里没有写出的变体（其他伙伴、其他场景、附加功能）；这些行是规划表孤立项，必须归入某个单元或列入待决事项。
2. 一个章节里有多个互相独立的配置目标时，拆成多个单元。
3. 引用其他章节的步骤（“参见 x.y 节”）**不复制**，记为单元间依赖，在 CS 的协同段表达。
4. 同一个单元可能同时含有可复用的部署步骤（D 型）和特性配置（F 型），这种情况拆成子单元分别处理。

分类（判据见 SKILL §4 P1 的表）：

| 常见章节 | 典型分类 | 说明 |
|---|---|---|
| License 开关批量开启 | D 型 | 属于“License 前置”：开哪些 License 进 CS（运营商规范），开关方法属于 Atom |
| 软参 / 本局数据 / 接口对接 | D 型 | 每个接口或每类数据一个 CompoundTask 候选 |
| 对端 NF 对接 | D 型 | 通常是“对端 Profile + 服务 (+ 订阅)”的组合，复用价值高，优先查已有 CT |
| 明确的产品特性 | F 型 | 必须在 P2 中映射到 Feature |
| 平台可靠性、日志、自愈开关 | D 型 | 多为单命令；不足 3 条不同命令时直接引 AtomTask |
| 组网说明、GUI 操作、查询、回退脚本、调测 | N 型 | 回退脚本可作为 CS 约束或决策点的素材，但不编排 |

### 3.1 条件作用域（逐语句还原）

文档常用注释或正文限定“哪些语句在什么条件下执行”。作用域读错，会造成整段漏配或多配，所以必须逐语句还原：

| 条件形态 | 默认作用域 | 处理 |
|---|---|---|
| 代码块内的条件注释（“//以下仅 X 涉及”“//如下配置只有 X 场景需要”） | 从这条注释的**下一条语句**起，到**同一代码块结束**或下一条条件注释为止；注释**之前**的语句不受限定 | `corpus_summary` 的“逐语句作用域”表已列出每条语句受哪些注释约束；在时间线的“条件”列逐语句填写 |
| 步骤标题 / 正文中的条件（“如果已完成 X，此处无需配置”“本章节功能按需开启”） | 整个步骤或章节 | 时间线中该步骤的所有语句都标上这个条件 |
| 阶段性说明（“测试阶段 / 正式商用”“前期试商用 / 后期”） | 该说明所在的语句或步骤 | 建成决策点，每个选项对应执行 / 省略的具体语句 |
| 作用域无法确定（如注释后紧跟另一个代码块） | — | 标“作用域待确认”，在 P3 附原文行号请用户确认 |

条件语句还可能**修改无条件部分的对象**（例如在条件分支里往一个通用的组中追加成员）。这种依赖要在时间线中注明“修改对象：xxx（由第 n 行创建）”。

## 4. 实体映射（02-配置单元与映射.md）

### 4.1 映射信号与强度

| 信号 | 做法（`图谱接口.md` §4） | 强度 |
|---|---|---|
| 特性码明文 | 直接 `get_md(Feature)` | 强 |
| LKV 码 | License → 对应特性，并与 Feature 的「所需License」互相核对 | 强（两个方向一致）/ 中（只有单向） |
| 特性名或章节标题 | `search_graph(layer=特性层)` → 读概述核实语义 | 中 |
| 命令指纹 | `search_graph(type=Feature)`，看单元内多条命令是否集中命中同一特性。命中的若是子文档（激活、操作步骤等），沿其「属于特性」边回溯到概述，按概述计数 | 中（≥2 条命令集中命中同一特性）/ 弱（只命中 1 条） |
| 语义推断 | 无任何字面证据 | 弱，必须标“待确认” |

**只有弱证据的单元：不得据此建 FeatureTask。** 要么在 P3 请用户确认，要么先按 D 型建 CompoundTask。

### 4.2 02 文件的组成

`02-配置单元与映射.md` 依次包含：

1. **单元表**：

```markdown
| 单元 | 章节（行号） | 分类 | 配置类命令 | 映射 Feature | 证据（调用 → 结论） | 强度 | 已有 Task | 处理 |
|---|---|---|---|---|---|---|---|---|
| U07 <单元名> | x.y（L100–L130） | F | CMD1, CMD2 | {nf}@Feature@<查询所得码> | LKVxxx→License→对应特性=…；特性搜索命中同码 | 强 | FT 未建；2 个 atom 已建 | 新建 FT |
```

2. **语句级时间线**：每个 D / F 单元一张（格式见 `构建方法.md` §2），不能只写“节选”。
3. **复用记录**：每个 CT 候选单元一行：

```markdown
| 单元 | 本步骤命令集 | 查询（terms / 过滤） | 候选 CT（command_set） | Jaccard | 相位同义（目标 / 对象链 / 顺序） | 结论 |
|---|---|---|---|---|---|---|
```

4. **既有对象覆盖核对**：拟复用的 Atom / CT / FT 逐个核对它能否还原本单元的“参数=值”和步骤；不能还原的列出缺口，改列为“更新”。
5. **版本差异表**和**文档内冲突表**（§5）。

表中的 Feature 码等 ID 必须是查询得到的真实值，不能照抄示例。

## 5. 版本差异、文档内冲突与文档缺陷

文档版本与平台最新版本不同时，**以平台为准**。`check_params.py` 的每一项都要登记到下面两张表之一，并给出处理方式。

### 5.1 版本差异（文档 ↔ 平台）

| 情形 | 处理 |
|---|---|
| 命令在平台上不存在 | 不建 atom，不编排；登记“版本差异：命令不存在”，在 P3 中请用户决定（替代命令 / 放弃） |
| 参数名在平台上不存在 | Task 中不写该参数；登记“版本差异：参数不存在” |
| 取值不在枚举内 / 越界 / 类型不符 | **能确定是同一取值的不同写法**（大小写、下划线、`0` ↔ `VALUE_0` 这类可机械对应的）→ 写平台写法，并注明“文档写法 X”；**其他情况** → 标“冲突 / 版本差异待确认”，不写取值，在 P3 中列出 |
| 平台必选参数，文档语句未给出 | ADD 类命令：在 Atom / CT / FT 中按 `<规划值>` 列出，注明“文档未给出，需规划”；SET / MOD 类命令：注明“修改类命令须带当前值或 `<规划值>`” |

```markdown
| 单元 | 命令 | 参数 | 文档写法（行号） | 平台（版本）定义 | 判定 | 处理 |
|---|---|---|---|---|---|---|
```

### 5.2 文档内冲突（数据规划表 ↔ 配置脚本 ↔ 注释 / 正文）

同一份文档内部常有不一致：规划表与脚本取值不同、注释与脚本含义相反、正文与脚本步骤不符。处理原则：

- **默认以配置脚本为准**（脚本是实际执行的内容），并在资产中注明冲突；
- 冲突涉及“是否执行某段配置”或“范围”（不只是取值）的，必须在 P3 中请用户确认；
- 一律登记，不能挑着用某一方而不说明。

```markdown
| 单元 | 命令 / 参数 | 规划表（行号） | 脚本（行号） | 注释 / 正文（行号） | 采用 | 理由 |
|---|---|---|---|---|---|---|
```

### 5.3 文档缺陷

`corpus_summary` 的“解析异常”（参数名乱码、取值带空白、参数重复）以及明显的照抄错误（如段落标题与内容不符），登记为“文档缺陷 / 待核对”，资产中按最可能的含义处理并注明，不静默修正。

## 6. 运营商规范抽取（供 CS 使用）

在读文档的过程中，把以下三类内容单独摘录出来，P6 写进 CS 的 `## 运营商规范`：

| 类别 | 判据 | 例 |
|---|---|---|
| **强制项** | 文中写“必须 / 要求 / 需要开启 / 不能” | “执行 ADD SCTPLE 时交叉路径必须选 YES，端口 38412” |
| **推荐值** | 文中写“建议 / 推荐 / 可根据实际” | “精准寻呼参数为建议值，各省可按实际调整” |
| **规划规则** | 命名格式、编号规则、取值范围约定 | “INTERPLMNFQDN 按 pt<AMF Pointer>.set<Set Id>.region<Region Id>.amf.5gc.mnc<MNC>.mcc<MCC>.3gppnetwork.org 规划” |

- **按参数判定类别**：同一条命令的不同参数可能属于不同类别（如一个参数“必须”、另一个只是“建议”），不要把整条命令归为一类。
- **成员与对应关系是行为，不是局点数据**：组里放哪些成员、哪个号段对应哪个取值、对哪些对端配置某策略——这些关系决定配置结果，必须以“规则 / 清单”的形式进 CS（公开编号保留原值，局点标识用占位）。只写“每组一条”而不写成员构成，配置生成就无法还原。

**局点数据脱敏**：具体 IP 地址、实例名、UUID、FQDN 实值、主机名不写入任何资产。需要示意时使用占位形式（`<实例名>`、`<IPv6 地址>`）；PLMN、MCC/MNC、IMSI 前缀、公开的业务编号，可以作为运营商规范保留。脱敏掉的参数要在未入图清单中以 `- 局点数据：CMD.PARAM, …` 登记（lint 参数闭包据此放行）。
